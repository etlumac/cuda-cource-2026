# Lab 2: Matrix Multiplication — Матричное умножение

## Описание

Программа считает на GPU произведение матриц `C = A * B`, где `A` имеет размер `M×K`, `B` размер `K×N`, `C` размер `M×N`. Все числа типа `float`. Для этого есть два своих ядра в `src/kernels.cu`:

- `NaiveMatMulKernel`: один поток считает один элемент `C[i][j]` и все числа читает из глобальной памяти;
- `TiledMatMulKernel`: блок потоков считает кусок матрицы `C` размером `T×T` (тайл), а нужные куски `A` и `B` сначала кладёт в shared memory и уже оттуда считает.

Режим выбирается аргументом `--mode`: `naive` или `tiled` (по умолчанию `tiled`). Размер тайла и блока в программе равен 16. Другие размеры (8 и 32) нужны только для эксперимента в `tests/bench.cu` и `tests/verify.cu`.

Эталон для проверки: `cublasSgemm` из cuBLAS в режиме чистого FP32.
Состав папки:

- `src/main.cu`: разбор аргументов, чтение входного файла, запись результата;
- `src/kernels.cu`, `include/matmul.h`: ядра и функции, которые копируют данные на GPU, запускают ядро и забирают результат;
- `tests/verify.cu`: сравнение с cuBLAS;
- `tests/bench.cu`: замеры времени и GFLOP/s для naive, tiled и cuBLAS;
- `tests/bank.cu`: отдельный эксперимент с bank conflicts в shared memory;
- `tests/run_checks.sh`: проверки командной строки;
- `data/lab2.txt`, `data/lab2_expected.txt`: пример из задания и ожидаемый результат.


Аргументы:

- `--input <файл>`: входной текстовый файл;
- `--output <файл>`: файл для результата;
- `--mode <режим>`: `naive` или `tiled` (по умолчанию `tiled`);
- `--help`: справка, код возврата 0.

Формат входа: первая строка `M K N`, затем `M*K` чисел матрицы `A` и `K*N` чисел матрицы `B`. Обе матрицы идут по строкам, числа разделены пробельными символами, дробная часть через точку, значения читаются как `float`.

Формат результата: строка `M N`, затем `M` строк по `N` чисел матрицы `C`, девять значащих цифр. Логи программа печатает в `stdout`, ошибки в `stderr`.

Коды возврата: `0` успех; `1` ошибка выполнения (CUDA) или записи результата; `2` неверные аргументы или входные данные (в том числе нечитаемый файл и меньшее число значений, чем нужно).

Нулевые и отрицательные размеры: программа поддерживает только положительные `M`, `K`, `N`. Если один из них не положителен, она пишет сообщение в `stderr`, не создаёт выходной файл и завершается с кодом 2.

Ограничение: индексы элементов в ядрах имеют тип `int`, поэтому `M*K`, `K*N` и `M*N` должны быть меньше 2^31. Для текстового файла такие матрицы всё равно нереально большие.

## Реализация

**Порядок хранения.** Матрицы лежат в одномерном массиве по строкам (row-major). Элемент `A[i][k]` это `a[i*K + k]`, `B[k][j]` это `b[k*N + j]`, `C[i][j]` это `c[i*N + j]`. Например, `B[2][1]` для `B` размера `3×2` лежит под номером `2*2 + 1 = 5`.

**Сетка потоков.** Блок это `T×T` потоков, `x` отвечает за столбец `C`, `y` за строку. Блоков по каждой оси столько, чтобы накрыть всю `C`: `(N + T - 1) / T` по `x` и `(M + T - 1) / T` по `y`. Поток вычисляет `row = blockIdx.y*T + threadIdx.y` и `col = blockIdx.x*T + threadIdx.x`. Запись результата и чтение в naive-ядре защищены проверкой `row < M && col < N`.

**Naive-ядро.** Поток идёт по `t` от 0 до `K-1` и накапливает `sum += a[row*K + t] * b[t*N + col]`. Каждое число из `A` и `B` поток читает из глобальной памяти. Соседние потоки имеют соседние `col`, поэтому подряд идущие потоки читают подряд лежащие числа `B` (это хорошо для памяти), а потоки с одним `row` читают одно и то же число `A`.

**Tiled-ядро.** Блок объявляет два массива в shared memory, `tile_a[T][T]` и `tile_b[T][T]`, и идёт вдоль `K` кусками по `T`. Один шаг цикла:

1. Каждый поток кладёт в `tile_a` одно число из `A` (строка `row`, столбец `tile_index*T + threadIdx.x`) и в `tile_b` одно число из `B` (строка `tile_index*T + threadIdx.y`, столбец `col`).
2. `__syncthreads()`: ждём, пока все загрузят свою часть.
3. Каждый поток считает `T` слагаемых из shared memory: `sum += tile_a[threadIdx.y][t] * tile_b[t][threadIdx.x]`.
4. `__syncthreads()`: ждём, пока все досчитают, иначе следующая загрузка затрёт тайл, который кто-то ещё читает.

Схема для одного блока при `K = 3T` (каждая клетка это один тайл `T×T`):

```text
            +----+
            | B0 |
            +----+
            | B1 |
            +----+
            | B2 |
            +----+
+----+----+----+   +----+
| A0 | A1 | A2 |   | C  |      C = A0*B0 + A1*B1 + A2*B2
+----+----+----+   +----+
```

За три шага блок берёт по одному тайлу из полосы `A` в своих строках и из полосы `B` в своих столбцах, перемножает и прибавляет к сумме.

**Неполные тайлы.** Если размер не кратен `T`, числа за границей матрицы заменяются нулями при загрузке: `tile_a` получает `A[row][a_col]` только при `row < M && a_col < K`, иначе 0; `tile_b` получает `B[b_row][col]` только при `b_row < K && col < N`, иначе 0. Нули не меняют сумму. Все потоки блока обязательно доходят до обоих `__syncthreads()`: преждевременного `return` в ядре нет, иначе часть потоков не пришла бы на барьер. Проверяется только запись `C`: `if (row < M && col < N)`.

Пример для `127×65` на `65×257` и `T = 16`: сетка `17×8` блоков (257 = 16*16 + 1, 127 = 7*16 + 15), число шагов вдоль `K` равно 5 (65 = 4*16 + 1), на последнем шаге из 16 столбцов `A` настоящий только один, остальные 15 нули.

**Что переиспользуется.** В naive-ядре элемент `C[i][j]` требует `2K` чтений из глобальной памяти, и одни и те же числа `A[i][*]` читают все `N` потоков своей строки. В tiled-ядре каждое число, загруженное в shared memory, используют `T` потоков блока, поэтому обращений к глобальной памяти примерно в `T` раз меньше (при `T = 16` в 16 раз).

**Shared memory и регистры.** Размеры взяты из `nvcc -arch=sm_86 -Xptxas=-v` для `T = 16`:

| Ядро | Регистров на поток | Shared memory на блок | Spill |
| --- | --- | --- | --- |
| naive | 40 | 0 | нет |
| tiled | 38 | 2048 байт (`2*16*16*4`) | нет |

Для `T = 8` и `T = 32` shared memory на блок равна 512 и 8192 байт (по той же формуле), число регистров для них я не смотрела. Размер блока 256 потоков по 38-40 регистров занимает около 10 тысяч регистров, поэтому на один SM (65536 регистров, до 1536 потоков) помещается 6 блоков, то есть 1536 потоков, полная загрузка. Для `T = 8` блок из 64 потоков упирается в лимит 16 блоков на SM (1024 потока), для `T = 32` помещается один блок из 1024 потоков. В обоих случаях получается около 67% от максимума потоков. Эти оценки сделаны по характеристикам архитектуры 8.6, отдельно через профилировщик я их не проверяла.

**Ошибки CUDA.** Каждый вызов CUDA API проходит через функцию `Check`, после запуска ядра вызывается `cudaGetLastError()`, затем копирование результата и `cudaDeviceSynchronize()`. При ошибке сообщение уходит в `stderr`, код возврата 1.

**Память и копирование.** `MatMulOnGpu` выделяет три массива `cudaMalloc` (`A`, `B`, `C`), копирует `A` и `B` на GPU (H2D), запускает ядро, копирует `C` обратно (D2H) и освобождает память.

## Проверка корректности

**Эталон.** `cublasSgemm` в режиме `CUBLAS_PEDANTIC_MATH`: это чистый FP32 без TF32 и других ускоренных режимов. Мои ядра тоже считают в FP32, поэтому режимы сравнимы. cuBLAS ждёт матрицы по столбцам (column-major), а у меня по строкам. Массив по строкам, прочитанный по столбцам, это транспонированная матрица. Поэтому я считаю `C^T = B^T * A^T`: вызываю `cublasSgemm` с матрицами в обратном порядке (сначала `B`, потом `A`), а результат ложится ровно в нужном порядке по строкам.

**Входные данные** (`tests/verify.cu`): три вида для каждого размера: случайные числа от -10 до 10, целые числа от -4 до 4 (сумма считается точно), около половины нулей. Генератор `std::mt19937`, seed `M*1000003 + K*10007 + N*101 + вид`, для `B` seed на единицу больше, чем для `A`.

**Допуск.** Для элемента `C[i][j]` разница с cuBLAS не должна превышать `gamma(2K) * S[i][j]`, где `S[i][j]` это сумма модулей `A[i][t]*B[t][j]` по `t`, `gamma(q) = q*u / (1 - q*u)`, `u = 2^-24`. Это граница из задания; `S` я считаю тем же cuBLAS на матрицах из модулей `|A|` и `|B|`, и добавляю запас 0.1% на то, что `S` посчитана в FP32. Задание сравнивает с FP64-эталоном, у меня эталон FP32 cuBLAS. Разница двух FP32-результатов не больше суммы их отклонений от точного ответа, это не превышает выбранный допуск. NaN и бесконечности в результате считаются ошибкой.

| --- | --- | --- | --- | --- | --- | --- | --- |
| `tile[32][32]` | по строке | 32 | 2.6009 | 2.1586 | 2.1578 | 2.1586 | 1.00 |
| `tile[32][32]` | по столбцу | 32 | 34.3545 | 34.1578 | 27.9734 | 27.9727 | 12.96 |
| `tile[32][33]` | по столбцу | 33 | 2.0772 | 1.7999 | 1.8002 | 1.8002 | 0.83 |

Чтение по столбцу из `[32][32]`: слово `[i][y]` лежит под номером `i*32 + y`. Остаток от деления на 32 равен `y` для любого `i`, то есть все 32 потока warp'а попадают в один банк и обращения идут по очереди (32-кратный конфликт). Если добавить лишний столбец (`[32][33]`), слово `[i][y]` лежит под номером `i*33 + y`, остаток равен `(i + y) % 32` и для 32 разных `i` все банки разные, конфликта нет. Результаты вычислений для обоих столбцовых вариантов совпали. Ускорение в 15.5 раза меньше теоретических 32, потому что в цикле есть и другая работа (сложение, вычисление индексов). Почему вариант `[32][33]` на 17% быстрее, чем чтение по строке, где конфликтов тоже нет, я не выяснила, вероятно дело в вычислении адресов, и выводов на этом не строю.

В основном GEMM такого паттерна нет. При `T = 16` в warp'е два значения `threadIdx.y`. Чтение `tile_a[threadIdx.y][t]` даёт два разных слова (номера отличаются на 16, банки разные), остальные потоки читают те же слова (broadcast). Чтение `tile_b[t][threadIdx.x]` это 16 подряд лежащих слов, обе половины warp'а читают одни и те же. Конфликтов нет, поэтому padding в tiled-ядро я не добавляла.

## Выводы

**Откуда выигрыш tiled.** В tiled-ядре каждое число из `A` и `B` читается из глобальной памяти один раз на блок и дальше используется `T` потоками из shared memory, а в naive-ядре каждый поток читает всё сам. Обращений к глобальной памяти получается в `T` раз меньше. На моей карте tiled при этом быстрее naive всего в 1.3-1.5 раза (при блоке 16: 512³ даёт 940 и 1219 GFLOP/s, 1024³ даёт 970 и 1459, 2048³ даёт 935 и 1285). Это меньше, чем можно было бы ждать. Причин, как мне кажется, несколько, но профилировщиком я это не проверяла. Во-первых, naive-ядро и так частично выигрывает от кэшей L1 и L2 (потоки одной строки читают одни и те же числа `A`, чтение `B` склеено). Во-вторых, в tiled-ядре на каждое умножение приходятся два чтения из shared memory и барьеры `__syncthreads()`, а в каждом потоке всего одно накопление.

**Размер тайла.** Лучше всего почти везде работает 16 (например, 1459 GFLOP/s на 1024³ против 1119 для 8 и 1368 для 32). Тайл 8 слабее: переиспользование всего в 8 раз, а блоков по 64 потока много. Тайл 32 переиспользует больше всех, но блок из 1024 потоков занимает почти весь SM, помещается один блок, а потоки чаще ждут друг друга на барьерах. На самом большом размере (2048³) тайл 32 оказался чуть лучше 16 (1382 против 1285). Это уже ближе к шуму ноутбучной карты, поэтому уверенно я могу сказать только, что тайл 8 хуже остальных, а между 16 и 32 разница небольшая.

**Почему tiled уступает cuBLAS.** cuBLAS быстрее моего tiled в 5-8 раз (на 2048³ 9916 против 1285 GFLOP/s при блоке 16). Я не смотрела, что именно внутри, но известно, что хорошие реализации считают в каждом потоке сразу несколько элементов `C` и держат часть данных в регистрах, читают память широкими векторными загрузками, перекрывают загрузку следующего тайла и вычисления и подбирают размеры под конкретную архитектуру. В моём ядре один поток считает один элемент, и на одно умножение приходятся два чтения shared memory. Поэтому до cuBLAS ядру далеко, и обгонять его я не пыталась.

**Размер и накладные расходы.** На небольших матрицах (512³) cuBLAS не успевает выйти на максимум: 5699 GFLOP/s против 8263 на 1024³ и 9916 на 2048³. Время работы ядра меньше 0.05 мс, и заметную часть занимает сам запуск. Для моих ядер GFLOP/s почти не растут с размером. Копирования CPU↔GPU в этой работе я не измеряла. В программе `submission` они есть, и чем быстрее ядро (cuBLAS считает 2048³ за 1.7 мс), тем больше их доля в общем времени.

**Ограничения.** Размеры матриц ограничены индексами типа `int`. Размер тайла в экспериментах берётся из набора 8, 16, 32 (шаблонный параметр). Замеры сделаны на одной ноутбучной карте, поэтому разницу в несколько процентов я не интерпретирую.
